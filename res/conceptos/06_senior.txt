    java.util.concurrent es la caja de herramientas de Java para que varios hilos compartan datos sin pisarse y sin escribir synchronized a mano: contadores atómicos, mapas seguros, colas que esperan y pestillos de salida.
    Imagina el marcador del ring con tres jueces a la vez: si cada uno lee «7», suma uno y escribe «8», se han perdido dos puntos. AtomicInteger es un marcador que lee, suma y escribe de un solo golpe; CountDownLatch es el árbitro que no da la salida hasta que los cuatro robots han dicho «listo», y una BlockingQueue es la cinta del taller: el mecánico deja piezas y el montador se queda dormido delante si no llega ninguna.
    Se usa con AtomicInteger.incrementAndGet(), ConcurrentHashMap.merge(clave, 1, Integer::sum), CountDownLatch.countDown() y await(), y BlockingQueue.put() y take() (ArrayBlockingQueue, LinkedBlockingQueue). En el robot no hacen falta: el juego llama a cadaTurno siempre desde el mismo hilo y el Vigilante no deja que un robot cree hilos; se practican en los ejercicios del tema 20.
    El fallo típico es creer que dos operaciones seguras seguidas son una operación segura: if (!mapa.containsKey(k)) mapa.put(k, v); sobre un ConcurrentHashMap sigue siendo una carrera. Usa putIfAbsent, computeIfAbsent o merge, que lo hacen de una vez; y recuerda que size() es solo una estimación mientras otros escriben.
    Para un senior: AtomicInteger se basa en CAS (compare-and-set, una instrucción de la CPU como lock cmpxchg en x86; desde Java 9, vía VarHandle), y con mucha contención los reintentos se disparan: LongAdder (Java 8) reparte la cuenta en celdas por hilo y escala muchísimo mejor, a cambio de que sum() no sea una foto exacta. ConcurrentHashMap ya no usa segmentos desde Java 8: lee sin candados y bloquea solo la cubeta que escribe, así que la función de computeIfAbsent corre con esa cubeta bloqueada; hazla corta y no toques el mismo mapa dentro (desde Java 9 lanza IllegalStateException: «Recursive update»). Todo el paquete es de Doug Lea y llegó en Java 5 (JSR 166).

    java.util.concurrent is Java's toolbox for letting several threads share data without trampling on each other, and without writing synchronized by hand: atomic counters, safe maps, queues that wait, and starting gates.
    Picture the ringside scoreboard with three judges at once: each one reads "7", adds one and writes "8", and two points have vanished. AtomicInteger is a scoreboard that reads, adds and writes in one go; CountDownLatch is the referee who won't start the bout until all four robots have said "ready"; and a BlockingQueue is the workshop conveyor belt: the mechanic drops parts on it and the assembler dozes off in front of it while nothing arrives.
    You use it through AtomicInteger.incrementAndGet(), ConcurrentHashMap.merge(key, 1, Integer::sum), CountDownLatch.countDown() and await(), and BlockingQueue.put() and take() (ArrayBlockingQueue, LinkedBlockingQueue). Your robot doesn't need any of it: the game always calls cadaTurno (onTick) from the same thread, and the game's watchman (the Vigilante) doesn't let robots start threads; you practice it in the topic 20 exercises.
    The classic mistake is believing that two safe operations in a row make one safe operation: if (!map.containsKey(k)) map.put(k, v); on a ConcurrentHashMap is still a race. Use putIfAbsent, computeIfAbsent or merge, which do it in one step; and remember that size() is only an estimate while others are writing.
    For seniors: AtomicInteger is built on CAS (compare-and-set, a CPU instruction such as lock cmpxchg on x86; since Java 9 via VarHandle), and under heavy contention the retries pile up: LongAdder (Java 8) spreads the count over per-thread cells and scales far better, at the price of sum() not being an exact snapshot. ConcurrentHashMap has had no segments since Java 8: it reads without locks and locks only the bucket it writes to, so the function you pass to computeIfAbsent runs with that bucket locked; keep it short and never touch the same map inside it (since Java 9 that throws IllegalStateException: "Recursive update"). The whole package is Doug Lea's work and arrived in Java 5 (JSR 166).

es:
    volatile es una palabra que se pone delante de un atributo para decir: «este valor lo leen y lo escriben varios hilos; no te guardes copias, mira siempre el de verdad».
    Sin volatile, cada robot del equipo lleva en la muñeca una foto de la pizarra del árbitro y mira la foto en vez de la pizarra. El árbitro escribe «¡FIN DEL COMBATE!» y un robot sigue repartiendo puñetazos al aire durante horas porque su foto dice «combate en curso». volatile le obliga a levantar la vista a la pizarra cada vez.
    Se usa así: volatile boolean seguir = true; un hilo hace while (seguir) { … } y otro pone seguir = false. Garantiza visibilidad y orden (lo que el hilo escribió antes de la escritura volatile lo ve quien después la lee) y que un long o un double se lean enteros. En el robot no lo necesitas: todo pasa en el hilo del juego.
    El fallo típico es creer que volatile hace atómico contador++: son tres pasos (leer, sumar, escribir) y dos hilos pueden perder sumas. Para eso, AtomicInteger o synchronized; volatile sirve para banderas y para publicar un objeto ya construido, no para «leer, cambiar y escribir».
    Para un senior: el bucle que nunca acaba no suele ser culpa de la caché de la CPU (que es coherente), sino del JIT, que saca la lectura del bucle (hoisting) y convierte while (!parar) en while (true); por eso falla después de calentar y nunca en el depurador. En x86 leer un volatile cuesta casi lo mismo que una lectura normal y escribirlo lleva una barrera StoreLoad; si solo necesitas parte de esa semántica, VarHandle (Java 9) ofrece getAcquire/setRelease y getOpaque. El double-checked locking del singleton solo es correcto desde Java 5 (JSR 133) y con el campo volatile.

en:
    volatile is a word you put in front of a field to say: "several threads read and write this value; don't keep copies, always look at the real one."
    Without volatile, every robot on the team wears a photo of the referee's board on its wrist and looks at the photo instead of the board. The referee writes "FIGHT OVER!" and one robot keeps punching thin air for hours because its photo still says "fight in progress". volatile forces it to look up at the board every single time.
    It works like this: volatile boolean keepGoing = true; one thread runs while (keepGoing) { … } and another sets keepGoing = false. You get visibility and ordering (whatever a thread wrote before the volatile write is seen by anyone who reads it afterwards), and a long or double is never read half-written. Your robot doesn't need it: everything happens on the game's thread.
    The classic mistake is thinking volatile makes counter++ atomic: it is three steps (read, add, write), and two threads can lose increments. Use AtomicInteger or synchronized for that; volatile is for flags and for publishing a fully built object, not for read-modify-write.
    For seniors: the loop that never ends is rarely the CPU cache's fault (caches are coherent); it is the JIT hoisting the read out of the loop and turning while (!stop) into while (true), which is why it fails only after warm-up and never under the debugger. On x86 a volatile read costs about the same as a plain one, while a volatile write adds a StoreLoad fence; if you only need part of those semantics, VarHandle (Java 9) gives you getAcquire/setRelease and getOpaque. Double-checked locking for singletons has only been correct since Java 5 (JSR 133), and only with a volatile field.

=== interbloqueo

titulo.es: Interbloqueo
titulo.de: Deadlock

claves.es: interbloqueo, deadlock, bloqueo mutuo, el programa se queda colgado, los hilos se esperan entre si, orden de los candados, livelock, jstack
claves.de: deadlock, verklemmung, gegenseitige blockierung, programm hängt, threads warten aufeinander, sperrreihenfolge, livelock, jstack

es:
    Un interbloqueo pasa cuando dos (o más) hilos se quedan esperando cada uno algo que tiene el otro y, como ninguno suelta lo suyo, se quedan parados para siempre. El programa no falla con un error: se cuelga.
    Dos robots en el taller: Tuercas agarra la llave inglesa y espera el destornillador; Chispas agarra el destornillador y espera la llave inglesa. Ninguno suelta nada «por si acaso», y ahí siguen, mirándose fijamente, mientras el locutor rellena tres horas de retransmisión hablando del tiempo.
    En Java ocurre con synchronized o con ReentrantLock cuando dos hilos cogen los mismos candados en distinto orden. Para encontrarlo, jstack <pid> (o jcmd <pid> Thread.print) imprime «Found one Java-level deadlock» con quién espera a quién, y ThreadMXBean.findDeadlockedThreads() lo detecta desde el propio programa. En tu robot no puede pasar: hay un solo hilo y el Vigilante no deja crear más.
    Para evitarlo: coge siempre los candados en el mismo orden global (por ejemplo, por id), no llames a código ajeno (oyentes, callbacks) mientras tienes un candado cogido, y usa tryLock(tiempo, unidad) para rendirte a tiempo en lugar de esperar para siempre.
    Para un senior: un interbloqueo necesita las cuatro condiciones de Coffman a la vez (exclusión mutua, retener y esperar, sin expropiación y espera circular); rompe una y desaparece, y el orden global rompe la espera circular. Vigila a sus primos: el livelock (todos ceden a la vez y nadie avanza; se arregla esperando un tiempo al azar) y la inanición. Y con hilos virtuales (Java 21), un synchronized que se bloquea clavaba el hilo portador (pinning, resuelto en Java 24 con el JEP 491): con pocos portadores ocupados, el programa parecía interbloqueado sin estarlo.
de:
    Ein Deadlock entsteht, wenn zwei (oder mehr) Threads jeweils auf etwas warten, das der andere hält, und keiner das Seine loslässt: Sie stehen für immer still. Das Programm stürzt nicht mit einem Fehler ab, es hängt einfach.
    Zwei Roboter in der Werkstatt: Mutter hält den Schraubenschlüssel und wartet auf den Schraubenzieher, Funke hält den Schraubenzieher und wartet auf den Schraubenschlüssel. Keiner gibt etwas her, „man weiß ja nie“, und so starren sie sich an, während der Kommentator drei Stunden Sendezeit mit dem Wetter füllt.

Zum Aufspüren gibt jstack <pid> (oder jcmd <pid> Thread.print) „Found one Java-level deadlock“ aus, samt wer auf wen wartet, und ThreadMXBean.findDeadlockedThreads() erkennt es im Programm selbst. In deinem Roboter kann es nicht passieren: Es gibt nur einen Thread, und der Wächter (Vigilante) lässt keine weiteren zu.
    Vermeiden lässt es sich so: Nimm Sperren immer in derselben globalen Reihenfolge (zum Beispiel nach ID), ruf keinen fremden Code (Listener, Callbacks) auf, während du eine Sperre hältst, und nutze tryLock(zeit, einheit), um rechtzeitig aufzugeben, statt ewig zu warten.
    Für Senioren: Ein Deadlock braucht alle vier Coffman-Bedingungen zugleich (gegenseitiger Ausschluss, Halten und Warten, keine Verdrängung, zirkuläres Warten); brich eine, und er verschwindet – die globale Reihenfolge bricht das zirkuläre Warten. Achte auf die Verwandten: Livelock (alle weichen gleichzeitig aus, keiner kommt voran; hilft zufälliges Warten) und Verhungern. Und bei virtuellen Threads (Java 21) hat ein blockierendes synchronized den Träger-Thread festgenagelt (Pinning, behoben in Java 24 mit JEP 491): Mit wenigen belegten Trägern wirkte das Programm verklemmt, ohne es zu sein.
en:
    A deadlock happens when two (or more) threads are each waiting for something the other one holds, and since neither lets go, they stay stuck forever. The program doesn't crash with an error: it just hangs.
    Two robots in the workshop: Nuts grabs the wrench and waits for the screwdriver; Sparky grabs the screwdriver and waits for the wrench. Neither lets go "just in case", so there they stand, staring at each other, while the commentator fills three hours of airtime talking about the weather.
    In Java it happens with synchronized or ReentrantLock when two threads take the same locks in different orders. To find it, jstack <pid> (or jcmd <pid> Thread.print) prints "Found one Java-level deadlock" along with who is waiting for whom, and ThreadMXBean.findDeadlockedThreads() detects it from inside the program. It can't happen in your robot: there is only one thread, and the game's watchman (the Vigilante) won't let you create more.
    To avoid it: always take locks in the same global order (by id, for example), never call foreign code (listeners, callbacks) while holding a lock, and use tryLock(time, unit) to give up in time instead of waiting forever.
    For seniors: a deadlock needs all four Coffman conditions at once (mutual exclusion, hold and wait, no preemption, circular wait); break any one and it is gone, and global ordering breaks the circular wait. Watch out for its cousins: livelock (everyone steps aside at the same time and nobody moves; random back-off fixes it) and starvation. And with virtual threads (Java 21), a synchronized block that blocked used to pin the carrier thread (fixed in Java 24 by JEP 491): with a few carriers tied up, the program looked deadlocked without being so.

=== modelo_de_memoria

claves.de: speichermodell, java memory model, jmm, happens-before, umordnung, sichere veröffentlichung, data race, datenwettlauf

es:
    El modelo de memoria de Java son las reglas que dicen qué valor puede ver un hilo al leer una variable que ha escrito otro hilo. Sin esas reglas, «lo escribí antes» no significa «el otro ya lo ve».
    Imagina al locutor loco, que para ir más rápido reordena las frases de la retransmisión siempre que a ÉL le dé igual el resultado. Para el público, que es otro hilo, el orden puede salir patas arriba: «¡KO!» antes de «suena la campana». happens-before es el contrato que obliga a que ciertas frases lleguen en su orden.
    Hay happens-before (lo de antes se ve después) entre soltar un candado y volver a cogerlo (synchronized, Lock), escribir un volatile y leerlo, Thread.start() y el código del hilo, el final de un hilo y Thread.join(), y meter y sacar de una colección concurrente (BlockingQueue.put/take, Future.get); además es transitivo. Si dos hilos tocan la misma variable, al menos uno escribe y no hay happens-before entre ellos, es una carrera de datos y la JVM puede darte valores que parecen imposibles; en tu robot, con un solo hilo, no te afecta.
    El fallo típico es publicar un objeto sin sincronizar (pieza = new Pieza(80); en un atributo normal): otro hilo puede ver ya la referencia pero los atributos todavía a 0 o null, porque construir y publicar se pueden reordenar. Publica con volatile, final, una colección concurrente o un candado.
    Para un senior: los atributos final tienen una garantía especial (JSR 133, Java 5): acabado el constructor, quien vea la referencia ve los final bien puestos, salvo que dejes escapar this dentro del constructor. Reordenan tanto el JIT como la CPU, y ARM reordena bastante más que x86: código «que funciona» en un portátil Intel puede romperse en un Mac con chip M o en un servidor Graviton; para probarlo de verdad está jcstress, de OpenJDK. es:
    Un HashMap guarda los pares clave-valor en un array de cubetas: calcula un número a partir de la clave (hashCode()), lo usa para elegir cubeta y mete ahí el par. Buscar es repetir la cuenta e ir directo a esa cubeta, sin recorrerlo todo: por eso get() es casi instantáneo.
    El guardarropa del estadio tiene 16 ganchos. Al robot «Tuercas» le calculan un número con las letras de su nombre, le toca el gancho 5 y allí cuelga su capa. Si a «Chispas» también le toca el 5, las dos capas cuelgan juntas (una colisión) y hay que mirar las etiquetas una a una; y cuando hay demasiadas capas, el encargado compra el doble de ganchos y vuelve a colgarlo todo.
    put(k, v) hace hash = h ^ (h >>> 16) con h = k.hashCode() (mezcla los bits altos con los bajos), índice = hash & (capacidad - 1) (la capacidad es potencia de 2; por defecto, 16) y, dentro de la cubeta, compara con equals(). Cuando hay más entradas que capacidad × 0,75 (el factor de carga), duplica el array y redistribuye (rehash). En la memoria() del robot, que es un Map, las claves String ya traen equals y hashCode bien hechos.
    El fallo típico es usar como clave un objeto tuyo que sobrescribe equals pero no hashCode (o al revés): dos claves «iguales» caen en cubetas distintas y get() devuelve null. Peor aún: cambiar un atributo de una clave ya guardada, que cambia su hashCode y la deja perdida en la cubeta vieja. Usa claves inmutables (String, Integer, un record).
    Para un senior: desde Java 8, una cubeta con 8 o más elementos se convierte en un árbol rojinegro (si la tabla tiene al menos 64 cubetas; si no, se redimensiona), y el peor caso de búsqueda pasa de O(n) a O(log n), mejor aún si las claves son Comparable; llegó tras los ataques de denegación de servicio por colisiones de 2011-2012. Si sabes cuántas entradas habrá, HashMap.newHashMap(n) (Java 19) calcula la capacidad bien; new HashMap<>(n) no, porque n es la capacidad y no las entradas, y redimensiona antes de lo que crees. Para orden de inserción, LinkedHashMap; para varios hilos, ConcurrentHashMap, nunca un HashMap compartido (en Java 7 una carrera durante el rehash podía cerrar un ciclo en una cubeta y dejar un get() en bucle infinito).
de:
    Eine HashMap legt Schlüssel-Wert-Paare in einem Array von Buckets ab: Sie berechnet aus dem Schlüssel eine Zahl (hashCode()), wählt damit den Bucket und legt das Paar dort hinein. Suchen heißt, dieselbe Rechnung zu wiederholen und direkt zu diesem Bucket zu gehen, ohne alles abzusuchen: Darum ist get() fast sofort fertig.
    Die Garderobe des Stadions hat 16 Haken. Für den Roboter „Mutter“ wird aus den Buchstaben seines Namens eine Zahl berechnet, er bekommt Haken 5, und dort hängt sein Umhang. Bekommt „Funke“ auch die 5, hängen beide Umhänge zusammen (eine Kollision), und man muss die Schildchen einzeln lesen; und wenn zu viele Umhänge hängen, kauft der Garderobier doppelt so viele Haken und hängt alles neu auf.
    put(k, v) rechnet hash = h ^ (h >>> 16) mit h = k.hashCode() (mischt die oberen mit den unteren Bits), index = hash & (kapazitaet - 1) (die Kapazität ist eine Zweierpotenz, standardmäßig 16) und vergleicht im Bucket mit equals(). Gibt es mehr Einträge als Kapazität × 0,75 (der Ladefaktor), verdoppelt sie das Array und verteilt neu (Rehash). In memoria() (gedaechtnis) des Roboters, einer Map, bringen String-Schlüssel equals und hashCode schon richtig mit.
    Der typische Fehler: als Schlüssel ein eigenes Objekt zu nehmen, das equals überschreibt, aber nicht hashCode (oder umgekehrt). Zwei „gleiche“ Schlüssel landen in verschiedenen Buckets, und get() liefert null. Noch schlimmer: ein Attribut eines schon gespeicherten Schlüssels zu ändern, was seinen hashCode ändert und ihn im alten Bucket verloren zurücklässt. Nimm unveränderliche Schlüssel (String, Integer, einen Record).
    Für Senioren: Seit Java 8 wird ein Bucket mit 8 oder mehr Elementen in einen Rot-Schwarz-Baum umgewandelt (wenn die Tabelle mindestens 64 Buckets hat; sonst wird vergrößert), und der schlechteste Fall der Suche sinkt von O(n) auf O(log n), noch besser bei Comparable-Schlüsseln; das kam nach den Denial-of-Service-Angriffen mit Hash-Kollisionen von 2011/2012. Weißt du, wie viele Einträge kommen, rechnet HashMap.newHashMap(n) (Java 19) die Kapazität richtig aus; new HashMap<>(n) nicht, denn n ist die Kapazität und nicht die Zahl der Einträge, und es vergrößert früher, als du denkst. Für Einfügereihenfolge LinkedHashMap; für mehrere Threads ConcurrentHashMap, nie eine geteilte HashMap (in Java 7 konnte ein Race während des Rehash einen Zyklus in einem Bucket schließen und ein get() in eine Endlosschleife schicken).
en:
    A HashMap stores key-value pairs in an array of buckets: it computes a number from the key (hashCode()), uses it to pick a bucket and puts the pair there. Looking something up means repeating the calculation and going straight to that bucket without scanning everything, which is why get() is almost instant.
    The stadium cloakroom has 16 hooks. For the robot "Nuts" they work out a number from the letters of its name, it gets hook 5, and its cape hangs there. If "Sparky" also gets 5, both capes hang together (a collision) and you have to read the tags one by one; and once there are too many capes, the attendant buys twice as many hooks and rehangs everything.
    put(k, v) computes hash = h ^ (h >>> 16) with h = k.hashCode() (mixing the high bits into the low ones), index = hash & (capacity - 1) (the capacity is a power of 2, 16 by default) and, inside the bucket, compares with equals(). When there are more entries than capacity × 0.75 (the load factor), it doubles the array and redistributes (rehash). In the robot's memoria() (memory), which is a Map, String keys already come with proper equals and hashCode.
    The classic mistake is using as a key an object of yours that overrides equals but not hashCode (or vice versa): two "equal" keys land in different buckets and get() returns null. Worse still: changing a field of a key that's already stored, which changes its hashCode and leaves it lost in the old bucket. Use immutable keys (String, Integer, a record).
    For seniors: since Java 8, a bucket with 8 or more entries is turned into a red-black tree (if the table has at least 64 buckets; otherwise it resizes), and the worst-case lookup drops from O(n) to O(log n), better still if the keys are Comparable; this came after the hash-collision denial-of-service attacks of 2011-2012. If you know how many entries there will be, HashMap.newHashMap(n) (Java 19) works out the capacity correctly; new HashMap<>(n) doesn't, because n is the capacity, not the number of entries, so it resizes sooner than you think. For insertion order, LinkedHashMap; for several threads, ConcurrentHashMap, never a shared HashMap (in Java 7 a race during rehash could close a cycle in a bucket and send a get() into an infinite loop).
