es:
    Con var dejas que Java deduzca el tipo de una variable local mirando lo que le asignas: en vez de escribir el tipo, escribes var. La variable sigue teniendo un tipo fijo; solo que lo pone el compilador.
    Es como el locutor que, en vez de anunciar «¡Llega Robot-de-Combate-Modelo-Cobalto-Con-Martillo, un robot de combate modelo cobalto con martillo!», grita «¡Llega ESE!» y señala: todo el estadio ve qué es. Pero si señala una caja cerrada, nadie sabe qué hay dentro.
    Llegó en Java 10 y solo vale dentro de los métodos: var enemigos = enemigosVistos(); es una List<Enemigo>, y var d = e.distancia(); un double. También sirve en el for (for (var e : enemigosVistos())) y, desde Java 11, en los parámetros de una lambda ((var a, var b) -> a + b), útil para ponerles anotaciones.
    El fallo típico: creer que var es «de cualquier tipo», como en JavaScript. No: tras var x = 5; x es un int para siempre, y x = "hola"; no compila. Tampoco vale sin valor (var x;), con null (var x = null;), con un array a pelo (var a = {1, 2};), en atributos ni en parámetros de métodos.
    La trampa sutil: var lista = new ArrayList<>(); deduce ArrayList<Object> (el diamante no tiene de dónde sacar el tipo), y var siempre deduce el tipo concreto (ArrayList, no List), así que la variable queda atada a la implementación. Úsalo cuando el lado derecho ya diga el tipo (new Pieza(), un literal) y evítalo cuando lo esconda (var r = calcular(); ¿qué es r?). Curiosidad: var no es palabra reservada sino «nombre de tipo reservado», así que var var = 1; compila (no lo hagas).

Ohne Wert (var x;), mit null (var x = null;), mit nacktem Array-Initialisierer (var a = {1, 2};), bei Attributen und Methodenparametern geht es ebenfalls nicht.
    Die feine Falle: var liste = new ArrayList<>(); wird zu ArrayList<Object> (der Diamant hat nichts, woraus er den Typ ableiten könnte), und var nimmt immer den konkreten Typ (ArrayList, nicht List), womit die Variable an die Implementierung gebunden ist. Nimm es, wenn die rechte Seite den Typ schon verrät (new Pieza(), ein Literal), und lass es, wenn es ihn versteckt (var r = berechne(); was ist r?). en:
    With var you let Java work out the type of a local variable from whatever you assign to it: instead of writing the type, you write var. The variable still has one fixed type; the compiler just fills it in.
    It is like the announcer who, instead of bellowing “Here comes Combat-Robot-Model-Cobalt-With-Hammer, a combat robot, model cobalt, with a hammer!”, just yells “Here comes THAT ONE!” and points: the whole stadium can see who he means. But if he points at a closed crate, nobody knows what is inside.
    It arrived in Java 10 and only works inside methods: what enemigosVistos (seenEnemies) returns is a List<Enemigo> in var enemies = enemigosVistos();, and var d = e.distancia(); is a double. It also works in a for loop (for (var e : enemigosVistos())) and, since Java 11, on lambda parameters ((var a, var b) -> a + b), handy when you want to annotate them.
    The classic mistake: thinking var means “any type”, as in JavaScript. It doesn't: after var x = 5; x is an int forever, and x = "hello"; does not compile. It also fails with no value (var x;), with null (var x = null;), with a bare array initializer (var a = {1, 2};), on fields and on method parameters.
    The subtle trap: var list = new ArrayList<>(); gives you ArrayList<Object> (the diamond has nothing to infer from), and var always picks the concrete type (ArrayList, not List), which ties the variable to the implementation. Use it when the right-hand side already states the type (new Pieza(), a literal) and avoid it when it hides it (var r = compute(); what is r?). Fun fact: var is not a keyword but a “reserved type name”, so var var = 1; compiles (please don't).

es:
    Un record es una clase cortita hecha solo para llevar datos: escribes sus campos entre paréntesis y Java te regala el constructor, los métodos para leerlos, equals, hashCode y toString. Sus campos no se pueden cambiar después.
    Es la ficha que el árbitro grapa en la puerta del vestuario: «Cobalto, x 120, y 340, turno 312». Nadie la corrige con boli; si algo cambia, se imprime una ficha nueva y la vieja se archiva tal cual.
    Llegó en Java 16: record Avistamiento(String quien, double x, double y, int turno) {} y ya puedes escribir new Avistamiento(e.nombre(), e.x(), e.y(), turnoActual()). Los campos se leen con a.x() o a.quien() (sin get delante) y dos fichas con los mismos datos son equals, así que sirven de clave en un Map o para no apuntar dos veces lo mismo en un Set.
    El fallo típico: buscar a.getX() o intentar a.x = 5; (los campos son private final). Para «cambiar» uno, se crea otro: new Avistamiento(a.quien(), nuevaX, a.y(), a.turno()). Y para validar, el constructor compacto: record Pieza(int peso) { Pieza { if (peso < 0) throw new IllegalArgumentException("peso: " + peso); } }.
    Para el senior: la inmutabilidad es superficial; si un componente es una List, quien te la pasó puede cambiarla por fuera, así que cópiala en el constructor compacto con List.copyOf. Un record no puede heredar de otra clase (ya hereda de java.lang.Record) ni tener más atributos de instancia que sus componentes, pero sí implementar interfaces, tener métodos y miembros static. Los records anidados son static de por sí, y junto con sealed y los record patterns de Java 21 dan a Java sus «tipos de datos algebraicos».

=== sealed
nivel: 4
tema: 19
titulo.es: Clases selladas (sealed)
titulo.de: Versiegelte Klassen (sealed)
titulo.en: Sealed classes
claves.es: sealed, clase sellada, interfaz sellada, sellada, permits, non-sealed, jerarquia cerrada, sealed interface
claves.de: sealed, versiegelte klasse, versiegeltes interface, versiegelt, permits, non-sealed, geschlossene hierarchie
claves.en: sealed, sealed class, sealed interface, permits, non-sealed, closed hierarchy
ver: herencia, interfaz, pattern_matching, record
es:
    Una clase o interfaz sealed («sellada») dice exactamente quién puede heredar de ella, y nadie más. Es una familia con la lista de miembros cerrada.
    Es el reglamento de la liga: «las armas permitidas son martillo, sierra y láser, punto». Si alguien se presenta con un tirachinas casero, el árbitro (el compilador) no le deja ni pisar el ring.
    Llegó en Java 17: sealed interface Arma permits Martillo, Sierra, Laser {}. Cada hija tiene que declararse final (no tendrá hijas), sealed (sigue con lista cerrada) o non-sealed (vuelve a abrirse); los records ya son final y encajan de maravilla. La gracia: un switch sobre un Arma puede cubrir los tres casos sin default, y el compilador comprueba que no falta ninguno.
    El fallo típico: olvidar poner final, sealed o non-sealed en una hija (no compila), o dejar las hijas en otro paquete (tienen que estar en el mismo paquete, o en el mismo módulo si usas módulos). Si están todas en el mismo archivo, puedes omitir permits y Java las encuentra solo.
    Para el senior: su valor está en el switch exhaustivo; añades una cuarta arma y el compilador te señala cada switch que se ha quedado corto. Por eso poner default en esos switch es una trampa: apaga justo el aviso que querías. Si cambias la jerarquía y no recompilas el código del switch, Java 21 lanza MatchException en ejecución en vez de fallar en silencio. Úsalo para datos de formas conocidas (resultados, mensajes, eventos), no para jerarquías que otros deban ampliar.
de:
    Eine sealed („versiegelte“) Klasse oder ein sealed Interface legt genau fest, wer davon erben darf, und sonst niemand. Eine Familie mit geschlossener Mitgliederliste.
    Es ist das Ligareglement: „Erlaubte Waffen sind Hammer, Säge und Laser, Schluss.“ Taucht einer mit einer selbstgebastelten Steinschleuder auf, lässt ihn der Schiedsrichter (der Compiler) nicht einmal in den Ring.
    Seit Java 17: sealed interface Arma permits Martillo, Sierra, Laser {}. Jede Unterklasse muss final (keine eigenen Kinder), sealed (wieder mit geschlossener Liste) oder non-sealed (wieder offen) sein; Records sind ohnehin final und passen perfekt. Der Clou: Ein switch über eine Arma kann alle drei Fälle ohne default abdecken, und der Compiler prüft, dass keiner fehlt.
    Der typische Fehler: bei einer Unterklasse final, sealed oder non-sealed zu vergessen (kompiliert nicht) oder die Unterklassen in ein anderes Paket zu legen (sie müssen im selben Paket stehen, bzw. im selben Modul, wenn du Module benutzt). Stehen alle in derselben Datei, darfst du permits weglassen, Java findet sie selbst.
    Für Fortgeschrittene: Der eigentliche Wert liegt im erschöpfenden switch; kommt eine vierte Waffe dazu, zeigt dir der Compiler jeden switch, der jetzt zu kurz ist. Deshalb ist ein default in solchen switches eine Falle: Es schaltet genau die Warnung ab, die du wolltest. Änderst du die Hierarchie und kompilierst den switch-Code nicht neu, wirft Java 21 zur Laufzeit eine MatchException, statt still falsch zu rechnen. Nimm es für Daten mit bekannten Formen (Ergebnisse, Nachrichten, Ereignisse), nicht für Hierarchien, die andere erweitern sollen.
en:
    A sealed class or interface states exactly who may extend it, and nobody else. It is a family with a closed membership list.
    It is the league rulebook: “the permitted weapons are hammer, saw and laser, full stop”. If someone turns up with a homemade slingshot, the referee (the compiler) won't even let them set foot in the ring.
    It arrived in Java 17: sealed interface Arma permits Martillo, Sierra, Laser {}. Every subtype must be declared final (no children of its own), sealed (another closed list) or non-sealed (open again); records are already final and fit perfectly. The payoff: a switch over an Arma can cover the three cases with no default, and the compiler checks that none is missing.
    The classic mistake: forgetting final, sealed or non-sealed on a subtype (it won't compile), or putting the subtypes in another package (they must live in the same package, or the same module if you use modules). If they are all in the same file, you may leave out permits and Java finds them itself.
    For seniors: the real value is the exhaustive switch; add a fourth weapon and the compiler points at every switch that is now incomplete. That is why a default in those switches is a trap: it silences exactly the warning you wanted. If you change the hierarchy and don't recompile the switch code, Java 21 throws a MatchException at run time instead of silently doing the wrong thing. Use it for data with known shapes (results, messages, events), not for hierarchies others are meant to extend.

=== pattern_matching
nivel: 4
tema: 19
titulo.es: Pattern matching
titulo.de: Pattern Matching

claves.es: pattern matching, coincidencia de patrones, instanceof con patron, record patterns, patron de record, switch con patrones, case when, desestructurar
claves.de: pattern matching, mustervergleich, musterabgleich, instanceof mit muster, record patterns, switch mit mustern, case when, destrukturieren
claves.en: pattern matching, instanceof pattern, type pattern, record patterns, switch patterns, case when, guarded pattern, destructuring

es:
    Pattern matching es preguntar «¿esto tiene tal forma?» y, si la tiene, sacar sus piezas con nombre en el mismo paso. Te ahorra el cast y las variables de apaño.
    Es el escáner de la entrada de la arena: «si es un robot volador, ponle la etiqueta V; si es una ficha de avistamiento, saca su x y su y y apunta». Mira, reconoce y desmonta en un solo gesto, sin preguntar dos veces.
    Hay tres sabores. instanceof con patrón (Java 16): if (o instanceof String texto) decir(texto); y texto ya es un String, sin cast. Switch con patrones (Java 21): case Martillo m -> …, con guardas como case Enemigo e when e.vuela() -> …. Y record patterns (Java 21): case Avistamiento(String n, double x, double y) -> apuntarA(x, y); desmonta el record de golpe.
    El fallo típico: poner el caso general antes que el concreto (case Object o antes de case String s); el compilador protesta porque el segundo nunca se alcanzaría (se llama dominancia). Y la variable del patrón solo existe donde el patrón es seguro: después de if (!(o instanceof String t)) return; sí puedes usar t, pero no en la rama en la que el patrón falló.
    Para el senior: un switch con patrones lanza NullPointerException si le llega null, salvo que añadas case null (Java 21). Los patrones sin nombre con _ (case Avistamiento(var n, _, _) ->) son de Java 22, y los patrones con tipos primitivos siguen en preview desde Java 23. Junto con sealed sustituyen a muchos Visitor: añades operaciones sin tocar las clases y el compilador vigila que no falte ningún caso.
de:
    Pattern Matching heißt: fragen „Hat das diese Form?“ und, wenn ja, im selben Schritt seine Teile mit Namen herausholen. Das spart den Cast und die Hilfsvariablen.
    Es ist der Scanner am Eingang der Arena: „Ist es ein fliegender Roboter, kleb ihm das Etikett F auf; ist es eine Sichtungskarte, nimm x und y heraus und ziel.“ Hinschauen, erkennen und zerlegen in einem Handgriff, ohne zweimal zu fragen.
    Es gibt drei Sorten. instanceof mit Muster (Java 16): if (o instanceof String text) decir(text); und text ist schon ein String, ohne Cast (decir heißt bei dir sagen). switch mit Mustern (Java 21): case Martillo m -> …, mit Wächtern wie case Enemigo e when e.vuela() -> … (vuela (fliegt)). Und Record Patterns (Java 21): case Avistamiento(String n, double x, double y) -> apuntarA(x, y); zerlegt den Record auf einen Schlag (apuntarA (zielenAuf)).
    Der typische Fehler: den allgemeinen Fall vor den speziellen zu setzen (case Object o vor case String s); der Compiler beschwert sich, weil der zweite nie erreicht würde (das heißt Dominanz). Und die Mustervariable existiert nur dort, wo das Muster sicher passt: Nach if (!(o instanceof String t)) return; darfst du t benutzen, aber nicht in dem Zweig, in dem das Muster gescheitert ist.
    Für Fortgeschrittene: Ein switch mit Mustern wirft eine NullPointerException, wenn null ankommt, außer du schreibst case null (Java 21). Unbenannte Muster mit _ (case Avistamiento(var n, _, _) ->) kamen mit Java 22, und Muster mit primitiven Typen sind seit Java 23 noch Preview. Zusammen mit sealed ersetzen sie viele Visitor: Du fügst Operationen hinzu, ohne die Klassen anzufassen, und der Compiler passt auf, dass kein Fall fehlt.
en:
    Pattern matching means asking “does this have such-and-such a shape?” and, if it does, pulling out its parts by name in the same step. It saves you the cast and the throwaway variables.
    It is the scanner at the arena gate: “if it is a flying robot, stick the F label on it; if it is a sighting card, take out its x and y and aim”. Look, recognize and take apart in one move, without asking twice.
    There are three flavors. The instanceof pattern (Java 16): if (o instanceof String text) decir(text); and text is already a String, no cast (for you, decir is say). Pattern switch (Java 21): case Martillo m -> …, with guards like case Enemigo e when e.vuela() -> … (vuela (flies)). And record patterns (Java 21): case Avistamiento(String n, double x, double y) -> apuntarA(x, y); takes the record apart in one go (apuntarA (aimAt)).
    The classic mistake: putting the general case before the specific one (case Object o before case String s); the compiler complains because the second could never be reached (this is called dominance). And the pattern variable only exists where the pattern is guaranteed to have matched: after if (!(o instanceof String t)) return; you can use t, but not in the branch where the pattern failed.
    For seniors: a pattern switch throws NullPointerException when it gets null, unless you add case null (Java 21). Unnamed patterns with _ (case Avistamiento(var n, _, _) ->) arrived in Java 22, and primitive types in patterns have been in preview since Java 23. Together with sealed they replace many Visitors: you add operations without touching the classes, and the compiler makes sure no case is missing.

    Un hilo virtual es un hilo ligerísimo que gestiona el propio Java, no el sistema operativo. Cuesta tan poco que puedes tener un millón a la vez, uno por tarea.
    Los hilos normales son robots de verdad: caros, pesados, caben pocos en el hangar. Los virtuales son hologramas de robot: cuando uno se queda esperando (a que llegue la carta del rival, por ejemplo), se apaga y deja su sitio en el ring a otro; cuando llega la carta, vuelve a encenderse donde haya hueco.
    Llegaron en Java 21: Thread.startVirtualThread(tarea), Thread.ofVirtual().start(tarea) o, lo más práctico, try (var ex = Executors.newVirtualThreadPerTaskExecutor()) { … }, que crea un hilo nuevo para cada submit. Se programan como hilos normales, con código que espera tranquilamente (leer de la red, de un archivo, Thread.sleep) sin bloquear a nadie. En los robots tampoco se pueden usar: el Vigilante también los prohíbe.
    El fallo típico: esperar que aceleren el cálculo puro. No lo hacen: si tu tarea solo calcula (simular peleas, por ejemplo), no hay esperas que aprovechar, y al final todo corre sobre tantos hilos «portadores» como núcleos. Brillan cuando las tareas se pasan la vida esperando: servidores, llamadas a otros servicios, bases de datos.

Cuidado con ThreadLocal: un millón de hilos, un millón de copias; para pasar contexto está ScopedValue (definitivo en Java 25). Fueron preview en Java 19 y 20 (Proyecto Loom) y definitivos en Java 21 con el JEP 444.

    A virtual thread is a featherweight thread managed by Java itself, not by the operating system. It costs so little that you can have a million at once, one per task.
    Normal threads are real robots: expensive, heavy, only a few fit in the hangar. Virtual ones are robot holograms: when one has to wait (for the rival's letter to arrive, say), it switches off and gives its spot in the ring to another; when the letter arrives, it lights up again wherever there is room.
    They arrived in Java 21: Thread.startVirtualThread(task), Thread.ofVirtual().start(task) or, most practical, try (var ex = Executors.newVirtualThreadPerTaskExecutor()) { … }, which creates a fresh thread for every submit. You write them like normal threads, with code that calmly waits (reading from the network, from a file, Thread.sleep) without blocking anyone. Robots can't use them either: the Watchdog bans these too.
    The classic mistake: expecting them to speed up pure computation. They don't: if your task only computes (simulating fights, say), there is no waiting to exploit, and in the end everything runs on as many “carrier” threads as there are cores. They shine when tasks spend their lives waiting: servers, calls to other services, databases.
    For seniors: don't pool them (they are disposable: one per task); to limit how much happens at once, use a Semaphore. Up to Java 23, waiting inside a synchronized block pinned the thread to its carrier; Java 24 (JEP 491) fixed that, but calls into native code still pin. Careful with ThreadLocal: a million threads, a million copies; for passing context there is ScopedValue (final in Java 25). They were a preview in Java 19 and 20 (Project Loom) and became final in Java 21 with JEP 444.

    Diseñar bien las excepciones es decidir cuándo lanzar una, de qué tipo, con qué mensaje y quién debe atraparla. Una buena excepción dice qué falló, con qué valores y dónde; una mala lo esconde.
    Es el parte del árbitro tras un KO: «Cobalto cayó en el turno 312: el brazo izquierdo se desenroscó al atacar con 0 de energía» sirve; «algo pasó» no sirve; y tirar el parte a la papelera (el catch vacío) es lo peor: el robot sigue peleando sin brazo y nadie sabe por qué.

En el juego, si tu robot lanza una excepción, la pelea la atrapa y la escribe en tu consola con su tipo, su mensaje y la línea: un buen mensaje te ahorra media hora.
