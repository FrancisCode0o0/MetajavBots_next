es:
    Una clase es un plano: describe qué datos tendrá una cosa (sus atributos) y qué sabrá hacer (sus métodos), pero ella misma todavía no es ninguna cosa concreta.
    Es el plano del robot clavado con chinchetas en la pared del taller: «dos brazos, una cabeza, blindaje 100, sabe dar puñetazos». Ningún rival ha caído KO por un papel, pero con ese único plano el taller puede fabricar cien robots iguales.
    En Java se escribe class Nombre { … } con los atributos y los métodos dentro de las llaves; por costumbre, el nombre empieza por mayúscula (Pieza, Arma, String). Tu robot ya es una clase: public class MiRobot extends Metajavbot es el plano con el que el juego construye tu luchador al empezar cada pelea.
    El fallo típico: confundir el plano con lo construido y esperar que la clase Pieza tenga «su» blindaje; el blindaje lo tiene cada pieza fabricada. Y otro: un archivo .java solo admite una clase public, y el archivo se ha de llamar como ella (MiRobot.java).
    Para un senior: una buena clase tiene una sola razón para cambiar; si su nombre pide un «y» (MotorYRadarYMarcador), está pidiendo partirse en tres.
de:
    Eine Klasse ist ein Bauplan: Sie beschreibt, welche Daten ein Ding haben wird (seine Attribute) und was es können wird (seine Methoden), ist selbst aber noch kein konkretes Ding.
    Sie ist der Roboterbauplan, der in der Werkstatt mit Reißzwecken an der Wand hängt: „zwei Arme, ein Kopf, Panzerung 100, kann boxen“. Von einem Blatt Papier ist noch kein Gegner k. o. gegangen, aber mit diesem einen Plan baut die Werkstatt hundert gleiche Roboter.
    In Java schreibst du class Name { … }, und Attribute und Methoden kommen zwischen die geschweiften Klammern; der Name beginnt üblicherweise mit einem Großbuchstaben (Pieza, Arma, String). Dein Roboter ist schon eine Klasse: public class MiRobot extends Metajavbot ist der Plan, nach dem das Spiel zu Beginn jedes Kampfes deinen Kämpfer baut.
    Der typische Fehler: Plan und gebautes Ding zu verwechseln und zu erwarten, dass die Klasse Pieza „ihre“ Panzerung hat – die hat jedes gebaute Teil für sich. Und noch einer: Eine .java-Datei darf nur eine public-Klasse enthalten, und die Datei muss genauso heißen (MiRobot.java).
    Für Seniors: Eine gute Klasse hat genau einen Grund, sich zu ändern; braucht ihr Name ein „Und“ (MotorUndRadarUndAnzeige), will sie in drei Klassen zerlegt werden.
en:
    A class is a blueprint: it describes what data a thing will have (its attributes) and what it will be able to do (its methods), but it is not yet any actual thing itself.
    It is the robot blueprint pinned to the workshop wall: “two arms, one head, armor 100, can punch”. No opponent has ever been knocked out by a sheet of paper, but from that single blueprint the workshop can build a hundred identical robots.
    In Java you write class Name { … } with the attributes and methods inside the braces; by convention the name starts with a capital letter (Pieza, Arma, String). Your robot is already a class: public class MiRobot extends Metajavbot is the blueprint the game uses to build your fighter at the start of every fight.
    The classic mistake: confusing the blueprint with what is built from it and expecting the class Pieza to have “its” armor; each part that gets built has its own. Another one: a .java file may hold only one public class, and the file must be named after it (MiRobot.java).
    For seniors: a good class has exactly one reason to change; if its name needs an “and” (EngineAndRadarAndScoreboard), it is asking to be split in three.

es:
    Un objeto es una cosa concreta construida con el plano de una clase: tiene sus propios datos (este blindaje, este nombre) y sabe hacer lo que el plano dice. También se le llama instancia.
    Del mismo plano salen tres robots por la cinta del taller: idénticos al nacer, pero si al primero le arrancan un brazo, los otros dos siguen saludando con los dos suyos. Cada robot construido es un objeto, con sus abolladuras propias.
    En Java se construye con new (Pieza casco = new Pieza();) y se usa con un punto: casco.blindaje, casco.recibirDano(10). Ya los usas sin saberlo: el Enemigo e que te llega en alVerEnemigo es un objeto, y e.distancia() se lo pregunta a ese rival en concreto; hasta "hola" es un objeto String.
    El fallo típico: usar una variable que todavía no apunta a ningún objeto (vale null) y llevarse un NullPointerException. Otro: creer que dos objetos con los mismos datos son el mismo; son gemelos, no la misma persona (de eso van == y equals).
    Para un senior: un objeto es identidad, estado y comportamiento; vive en el montón (heap) y el recolector lo retira cuando ya nadie lo referencia, así que crear objetos pequeños en cada turno es barato, pero no gratis.
de:
    Ein Objekt ist ein konkretes Ding, gebaut nach dem Bauplan einer Klasse: Es hat seine eigenen Daten (diese Panzerung, diesen Namen) und kann, was der Plan vorsieht. Man nennt es auch Instanz.
    Aus demselben Plan laufen drei Roboter vom Fließband: bei der Geburt völlig gleich, aber reißt man dem ersten einen Arm ab, winken die anderen beiden weiter mit beiden Armen. Jeder gebaute Roboter ist ein Objekt, mit seinen ganz eigenen Beulen.
    In Java baust du es mit new (Pieza casco = new Pieza();) und benutzt es mit einem Punkt: casco.blindaje, casco.recibirDano(10). Du benutzt längst welche: Der Enemigo (Gegner) e, den du in alVerEnemigo (beiSicht) bekommst, ist ein Objekt, und e.distancia() (entfernung) fragt genau diesen Gegner; sogar "hallo" ist ein String-Objekt.
    Der typische Fehler: eine Variable zu benutzen, die noch auf kein Objekt zeigt (sie ist null), und eine NullPointerException zu kassieren. Ein anderer: zu glauben, zwei Objekte mit denselben Daten seien dasselbe – sie sind Zwillinge, nicht dieselbe Person (darum geht es bei == und equals).
    Für Seniors: Ein Objekt ist Identität, Zustand und Verhalten; es lebt auf dem Heap, und der Garbage Collector räumt es weg, sobald niemand mehr darauf verweist – kleine Objekte in jedem Zug zu erzeugen ist also billig, aber nicht umsonst.
en:
    An object is an actual thing built from a class's blueprint: it has its own data (this armor, this name) and can do whatever the blueprint says. It is also called an instance.
    Three robots roll off the workshop conveyor from the same blueprint: identical at birth, but if the first one loses an arm, the other two keep waving with both of theirs. Each robot built is an object, with its very own dents.
    In Java you build one with new (Pieza casco = new Pieza();) and use it with a dot: casco.blindaje, casco.recibirDano(10). You already use them: the Enemigo (Enemy) e you get in alVerEnemigo (onSeeEnemy) is an object, and e.distancia() (distance) asks that particular rival; even "hello" is a String object.
    The classic mistake: using a variable that does not point to any object yet (it is null) and getting a NullPointerException. Another: believing two objects with the same data are the same one; they are twins, not the same person (that is what == versus equals is about).
    For seniors: an object is identity, state and behavior; it lives on the heap and the garbage collector reclaims it once nobody refers to it, so creating small objects every tick is cheap, but not free.

ejemplo:
    class Pieza {                           // el plano || der Bauplan || the blueprint
        double blindaje = 100;
    }

    public class MiRobot extends Metajavbot {
        Pieza casco = new Pieza();          // un objeto || ein Objekt || one object
        Pieza escudo = new Pieza();         // otro, del mismo plano || ein zweites, vom selben Plan || another, same blueprint

        @Override
        public void alRecibirGolpe(Golpe g) {
            casco.blindaje -= g.dano();     // solo se abolla el casco || nur der Helm bekommt Beulen || only the helmet gets dented
            escribir(casco.blindaje + " / " + escudo.blindaje);
        }
    }

=== new

es:
    new es la palabra que manda fabricar un objeto nuevo a partir de una clase: le reserva memoria, le da sus valores iniciales y te devuelve dónde ha quedado.
    Es el botón rojo y gordo de la cadena de montaje: metes el plano, lo aporreas y, entre ruido de prensa y algo de humo, sale un robot recién pintado. Cada pulsación, un robot más; aporrearlo dentro de un bucle de mil vueltas llena el taller de robots que nadie ha pedido.
    Se escribe new, el nombre de la clase y paréntesis, que llaman a su constructor: new Pieza(), new StringBuilder("¡"), new Random(42), new ArrayList<>(). El resultado se guarda en una variable para usarlo después: List<String> vistos = new ArrayList<>();
    El fallo típico: declarar la variable y olvidar el new, así que vale null y el primer vistos.add() revienta con NullPointerException. El otro: hacer el new dentro de cadaTurno de algo que debía durar toda la ronda, y perder lo guardado porque en cada turno estrenas un objeto vacío.
    Para un senior: new siempre da un objeto distinto (new String("a") != "a"), mientras que las fábricas como List.of() o Integer.valueOf(5) pueden reutilizar uno; además, la JVM abarata el new (asignación rápida en el TLAB, recolección barata de los de vida corta) y el JIT a veces ni lo crea gracias al análisis de escape.

    new ist das Wort, das ein neues Objekt nach dem Plan einer Klasse herstellen lässt: Es reserviert Speicher, setzt die Anfangswerte und gibt dir zurück, wo das Objekt liegt.
    Es ist der dicke rote Knopf am Fließband: Plan einlegen, draufhauen, und unter Pressengedröhn und etwas Qualm rollt ein frisch lackierter Roboter heraus. Jeder Druck ein Roboter mehr; haust du in einer Schleife mit tausend Runden drauf, steht die Werkstatt voller Roboter, die keiner bestellt hat.

Der andere: etwas, das die ganze Runde halten soll, in cadaTurno (jedenZug) mit new zu erzeugen und alles Gespeicherte zu verlieren, weil du jeden Zug mit einem leeren Objekt anfängst.
    Für Seniors: new liefert immer ein eigenes Objekt (new String("a") != "a"), Fabrikmethoden wie List.of() oder Integer.valueOf(5) dürfen dagegen eines wiederverwenden; außerdem macht die JVM new billig (schnelle Allokation im TLAB, kurzlebige Objekte werden günstig eingesammelt), und der JIT spart es dank Escape-Analyse manchmal ganz ein.
en:
    new is the word that has a fresh object built from a class: it reserves memory for it, sets its starting values and hands you back where it ended up.
    It is the big fat red button on the assembly line: slot in the blueprint, slam it, and amid press-machine thumping and a puff of smoke a freshly painted robot rolls out. Every press, one more robot; slam it inside a loop of a thousand laps and the workshop fills up with robots nobody ordered.
    You write new, the class name and parentheses, which call its constructor: new Pieza(), new StringBuilder("!"), new Random(42), new ArrayList<>(). You store the result in a variable to use it later: List<String> vistos = new ArrayList<>();

=== atributo
nivel: 2

titulo.es: Atributo

es:
    Un atributo (o campo) es una variable que pertenece a un objeto: se declara dentro de la clase, fuera de los métodos, y guarda lo que ese objeto es o recuerda.
    Son las pegatinas del costado del robot: «blindaje 87», «golpes dados 4», «nombre: El Tostadoras». Cada robot lleva las suyas, y el locutor loco las lee a gritos cada vez que uno pasa por delante.
    Se declaran con tipo y nombre al principio de la clase (int golpesDados = 0; String apodo;) y cualquier método del objeto los lee y los cambia. En MiRobot, un atributo es la forma de recordar algo de un turno al siguiente; las variables declaradas dentro de cadaTurno nacen y mueren en cada turno.
    El fallo típico: declarar dentro del método lo que debía ser atributo, y que vuelva a 0 cada turno; o al revés, convertir en atributo cualquier cosa hasta no saber quién cambia qué. Si no le das valor, un atributo empieza en 0, false o null (una variable local sin valor, en cambio, ni compila).
    Para un senior: el conjunto de atributos es el estado del objeto, y cuanto menos estado mutable, menos fallos; hazlos private y final siempre que puedas, y no guardes en un atributo lo que se puede calcular al momento.
de:
    Ein Attribut (oder Feld) ist eine Variable, die zu einem Objekt gehört: Es wird in der Klasse, aber außerhalb der Methoden deklariert und speichert, was dieses Objekt ist oder sich merkt.
    Es sind die Aufkleber an der Seite des Roboters: „Panzerung 87“, „ausgeteilte Treffer 4“, „Name: Der Toaster“. Jeder Roboter trägt seine eigenen, und der verrückte Sprecher brüllt sie vor, sobald einer vorbeirollt.
    Du deklarierst sie mit Typ und Namen am Anfang der Klasse (int golpesDados = 0; String apodo;), und jede Methode des Objekts kann sie lesen und ändern. In MiRobot ist ein Attribut der Weg, sich etwas von einem Zug zum nächsten zu merken; Variablen, die in cadaTurno (jedenZug) deklariert sind, entstehen und vergehen in jedem Zug.
    Der typische Fehler: in der Methode zu deklarieren, was ein Attribut sein sollte, sodass es jeden Zug wieder 0 ist; oder umgekehrt alles zum Attribut zu machen, bis keiner mehr weiß, wer was ändert. Ohne Wert beginnt ein Attribut bei 0, false oder null (eine lokale Variable ohne Wert kompiliert dagegen gar nicht).
    Für Seniors: Die Attribute zusammen sind der Zustand des Objekts, und je weniger veränderlicher Zustand, desto weniger Fehler; mach sie private und final, wo es geht, und speichere nichts in einem Attribut, was sich jederzeit ausrechnen lässt.
en:
    An attribute (or field) is a variable that belongs to an object: it is declared inside the class but outside the methods, and it holds what that object is or remembers.
    They are the stickers on the robot's flank: “armor 87”, “hits landed 4”, “name: The Toaster”. Each robot wears its own, and the crazy announcer bellows them out whenever one rolls past.
    You declare them with a type and a name at the top of the class (int golpesDados = 0; String apodo;) and any method of the object can read and change them. In MiRobot, a field is how you remember something from one tick to the next; variables declared inside cadaTurno (onTick) are born and die every tick.
    The classic mistake: declaring inside the method what should be a field, so it is back to 0 every tick; or the opposite, turning everything into a field until nobody knows who changes what. Without a value, a field starts at 0, false or null (a local variable without a value doesn't even compile).
    For seniors: together the fields are the object's state, and the less mutable state, the fewer bugs; make them private and final whenever you can, and do not store in a field what you can compute on the spot.

=== constructor

claves.de: konstruktor, konstruktoren, standardkonstruktor, konstruktor mit parametern, objekt initialisieren, constructor

es:
    Un constructor es un método especial que se ejecuta solo al hacer new: deja el objeto recién nacido listo para usarse, con sus atributos ya con valor.
    Es el técnico que espera al final de la cadena de montaje: antes de soltar al robot en la arena, le atornilla los brazos que pediste, le llena el depósito y le pinta el nombre en la frente. Ningún robot sale del taller sin pasar por sus manos, ni siquiera el que se queja.
    Se escribe como un método con el mismo nombre que la clase y sin tipo de retorno: Arma(String tipo, double dano) { this.tipo = tipo; this.dano = dano; }, y se llama con new Arma("laser", 12). Si no escribes ninguno, Java pone uno vacío sin parámetros; puedes tener varios (sobrecarga) y uno puede llamar a otro con this(...).
    El fallo típico: escribirle un tipo de retorno (void Arma(...)), con lo que deja de ser constructor y pasa a ser un método raro que nadie llama. El otro: escribir un constructor con parámetros y descubrir que new Arma() ya no compila, porque el vacío de regalo desaparece en cuanto escribes uno tuyo.
    Para un senior: valida en el constructor (Objects.requireNonNull, IllegalArgumentException) para que no pueda existir ningún objeto inválido, y nunca llames desde él a métodos que se puedan sobrescribir: la subclase aún no ha inicializado sus atributos y verá nulls. Con muchos parámetros opcionales, mejor un builder o un método de fábrica estático.
de:
    Ein Konstruktor ist eine besondere Methode, die nur bei new läuft: Sie macht das frisch geborene Objekt einsatzbereit, mit schon belegten Attributen.
    Er ist der Techniker am Ende des Fließbands: Bevor der Roboter in die Arena darf, schraubt er ihm die bestellten Arme an, füllt den Tank und malt ihm den Namen auf die Stirn. Kein Roboter verlässt die Werkstatt, ohne durch seine Hände zu gehen – auch nicht der, der sich beschwert.
    Man schreibt ihn wie eine Methode mit dem Namen der Klasse und ohne Rückgabetyp: Arma(String tipo, double dano) { this.tipo = tipo; this.dano = dano; }, und ruft ihn mit new Arma("laser", 12) auf. Schreibst du keinen, legt Java einen leeren ohne Parameter an; du kannst mehrere haben (Überladung), und einer kann mit this(...) einen anderen aufrufen.
    Der typische Fehler: ihm einen Rückgabetyp zu geben (void Arma(...)) – dann ist er kein Konstruktor mehr, sondern eine seltsame Methode, die niemand aufruft. Der andere: einen Konstruktor mit Parametern zu schreiben und festzustellen, dass new Arma() nicht mehr kompiliert, weil der geschenkte leere verschwindet, sobald du einen eigenen schreibst.
    Für Seniors: Prüfe im Konstruktor (Objects.requireNonNull, IllegalArgumentException), damit es gar keine ungültigen Objekte geben kann, und rufe darin nie überschreibbare Methoden auf: Die Unterklasse hat ihre Attribute noch nicht initialisiert und sieht nulls. Bei vielen optionalen Parametern ist ein Builder oder eine statische Fabrikmethode besser.
en:
    A constructor is a special method that runs only on new: it gets the newborn object ready to use, with its fields already set.
    It is the technician waiting at the end of the assembly line: before the robot is let loose in the arena, he bolts on the arms you ordered, fills the tank and paints its name on its forehead. No robot leaves the workshop without passing through his hands, not even the one that complains.
    You write it like a method named after the class with no return type: Arma(String tipo, double dano) { this.tipo = tipo; this.dano = dano; }, and you call it with new Arma("laser", 12). If you write none, Java adds an empty one with no parameters; you can have several (overloading) and one can call another with this(...).

es:
    Un método default es un método con cuerpo dentro de una interfaz: las clases que la implementan lo reciben hecho y, si quieren, lo sobrescriben. Las interfaces también pueden tener métodos static (de la interfaz, sin objeto) y private (ayudantes internos).
    El reglamento de los aparatos enchufables dice «todo aparato tiene un botón USAR»; un día la federación añade «y un botón AUTODESTRUCCIÓN, que por defecto hace un pfff triste y suelta confeti». Ningún fabricante tiene que rehacer su aparato: todos reciben el confeti de serie, y el que quiera explosiones de verdad, que lo sobrescriba.
    En Java: interface Arma { double dano(); default double danoCritico() { return dano() * 2; } static Arma deJuguete() { … } }. La biblioteca está llena de ellos: List.sort(c), Map.getOrDefault(k, v), Collection.removeIf(p) e Iterable.forEach(...) son default, y List.of(...) o Comparator.comparing(...) son métodos static de interfaz.
    El fallo típico: escribir un método con cuerpo en una interfaz sin la palabra default («interface abstract methods cannot have body»), o implementar dos interfaces con el mismo default y que no compile hasta que lo sobrescribas y elijas (Arma.super.danoCritico()). Y no metas estado ni lógica pesada: la interfaz no puede tener atributos de objeto, y una interfaz llena de código es una clase abstracta disfrazada.
    Para un senior: los default llegaron en Java 8 sobre todo para poder añadir métodos (como stream() o forEach) a interfaces ya publicadas sin romper a quien las implementaba; los private de interfaz, en Java 9. Siempre gana la clase sobre la interfaz, y la interfaz más concreta sobre la más general; y no se puede hacer default de equals, hashCode ni toString.

en:
    A default method is a method with a body inside an interface: classes implementing it get it ready-made and may override it if they want. Interfaces can also have static methods (belonging to the interface, no object needed) and private ones (internal helpers).
    The rulebook for plug-in gadgets says “every gadget has a USE button”; one day the federation adds “and a SELF-DESTRUCT button, which by default goes pfff sadly and spits confetti.” No manufacturer has to rebuild its gadget: they all get the confetti as standard, and whoever wants real explosions overrides it.
    In Java: interface Arma { double dano(); default double danoCritico() { return dano() * 2; } static Arma deJuguete() { … } }. The library is full of them: List.sort(c), Map.getOrDefault(k, v), Collection.removeIf(p) and Iterable.forEach(...) are default methods, while List.of(...) and Comparator.comparing(...) are static interface methods.
    The classic mistake: writing a method with a body in an interface without the word default (“interface abstract methods cannot have body”), or implementing two interfaces with the same default method, which won't compile until you override it and choose (Arma.super.danoCritico()). And do not put state or heavy logic in there: an interface cannot have instance fields, and an interface full of code is an abstract class in disguise.
    For seniors: default methods arrived in Java 8 mainly so methods (such as stream() or forEach) could be added to already published interfaces without breaking existing implementations; private interface methods came in Java 9. The class always wins over the interface, and the more specific interface over the more general one; and you cannot make equals, hashCode or toString a default method.
